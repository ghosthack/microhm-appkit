Microhm architecture

The native macOS (Swift/AppKit) port of micro-harness-manager. Agent and shell sessions run in a background daemon that outlives the app. The app or the headless host drives them over a Unix socket and exposes them to agents through MCP and to phones through a LAN web page.

Executables

Contents/MacOS/Microhm

The app

AppKit window with the session sidebar, terminal view, dialogs, settings and usage budgets. It owns the registry lock while open and runs MCP and the phone page in-process.

Contents/MacOS/microhm-mux

Daemon + CLI

One binary. microhm-mux serve is the long-lived PTY daemon, and the other subcommands are a CLI client. Sessions survive app restarts because they live here.

Contents/MacOS/microhm-host

Background host

Keeps MCP, the phone page and the menu-bar icon running after the app quits, then hands them back when the app reopens. The --phone-only mode serves just the phone page.

Key flows

Launch

Starting a session

  1. A user (New Session sheet), an agent (spawn) or the phone page asks for a harness in a project directory.
  2. SessionLauncher asks the harness plugin for its command and adds the MCP URL. The token goes in the environment or an owner-only config file, never on the command line.
  3. SessionServerHost.newSession sends new over the socket and starts the daemon first if it isn't running.
  4. The daemon forks a PTY and feeds its output into a HeadlessTerminal. The registry records the entry in sessions.json.
Status

State detection

  1. SessionStatusPoller captures each live session on a background queue, one capture in flight per session.
  2. A per-session StateDetector checks screen quiescence first (5 s short, 20 s long).
  3. The harness plugin's text patterns then refine the result to WORKING, WAITING_FOR_INPUT or IDLE.
  4. Results land on the main queue and update the sidebar badges.
MCP

Agents driving agents

  1. An agent calls a tool on 127.0.0.1:7402 using its session's token.
  2. SessionController turns it into daemon input, capture or wait calls and masks harness chrome with ScreenMask.
  3. read is incremental per caller and session, computed with ScreenDiff.
  4. notify registers a one-shot wait. A monitor re-checks it on the daemon's watch event stream.
Hand-off

App quits, sessions keep running

  1. As the app quits, HostLauncher starts microhm-host if any registered session is live.
  2. The host waits up to 30 s for instance.lock, then serves the same ports and tokens.
  3. When the app relaunches, it stops the host through HostOwner and takes the lock back.
  4. Incremental read state and pending notify waits don't survive the hand-off.
Phone

Phone page

  1. PhoneServer listens on every interface on :7403 and serves Resources/web unchanged.
  2. The user logs in once with POST /api/login and the token; a cookie carries it after that.
  3. /api/sessions, screen and stream (SSE) read state. send, keys, spawn, resume, close and upload act.
  4. The Settings window shows a QR code for pairing.
Interop

Java compatibility

  1. The mux protocol is wire-identical to the Java daemon, so either CLI drives either daemon.
  2. sessions.json keeps the Java format, and unknown fields and entries are preserved on save.
  3. The phone page and its tests are copies from upstream, pinned in Shared/shared.lock.
  4. Separate state directory and ports (7402/7403 vs Java 7392/7393) let the two run side by side.

Lifecycle: closing or quitting the app

Closing the last window quits the app (applicationShouldTerminateAfterLastWindowClosed returns true). Quitting ends only the app process. Sessions live in the daemon and keep running.

Quit sequence

applicationWillTerminate

  1. Stop the status timer, detach every terminal and remove the menu-bar icon.
  2. Stop the MCP and phone servers in CoreBackend.shutdown.
  3. Start microhm-host through HostLauncher.launchIfNeeded if it's needed.
  4. Wait at most 3 s for steps 2 and 3, so a stuck daemon can't hang the quit.
  5. Release instance.lock.
Daemon exit

When sessions actually stop

  1. The app never shuts the daemon down.
  2. The daemon exits on its own when its last session ends, unless it was started with --keep-alive.
  3. It also stops on microhm-mux shutdown, which kills every session.
  4. The host exits once no registered session is live or when the app reopens.
Hand-off cost

What agents lose

  1. Incremental read state: the next read returns the whole screen.
  2. Pending notify waits end.
  3. Ports, tokens and per-session MCP configs stay the same, so agents don't need to reconfigure.
